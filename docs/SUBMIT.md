# 提交飞牛应用中心

从「改完代码」到「审核通过」的操作清单。每次发版照做，字段口径不再逐次重新确认。

官方只接受表单提交，没有开发者后台，也没有公开 API。

## 2. 七条硬规则与 fnspeed 的落点

审核按这七条走。逐条自查，任何一条不过就不提交。

| # | 官方规则 | fnspeed 落点 | 核对方式 |
|---|---|---|---|
| 1 | root 权限应用无法上架 | `config/privilege` 用 `"run-as": "package"` | `cat config/privilege` |
| 2 | 鉴权优先接入统一网关、不监听公网端口 | `main.go` 绑 `127.0.0.1:8976`；`ui/config` 用 `gatewaySocket`；`checkport = false`；`fnspeed.sc` 的 `port_forward="no"` | `grep Addr src/main.go`、`grep checkport manifest` |
| 3 | platform 取值与提交前自测 | 双包：`platform = x86` / `arm` | 两个包分别 `tar xzOf ... manifest` |
| 4 | 文件读写接口需校验路径安全 | 只写自己的 `etc/` 与 `var/`，不接受用户传入路径，不读写 NAS 用户目录 | `grep -n 'filepath.Join\|WriteFile' src/store.go` |
| 5 | 付费内容需在介绍首行声明 | 无付费，不适用 | — |
| 6 | 版本号固定三段式 | 三处同步：`build.sh` 的 `VER`、`manifest` 的 `version`、本文件第 3 节 | `grep '^VER' build.sh; grep '^version' manifest` |
| 7 | 应用名称不得以「飞牛」为前缀 | `display_name = 带宽压测` | `grep display_name manifest` |

**规则 2 是 1.5.5 的主要改动点**，也是最容易踩的：只要进程绑到 `0.0.0.0`，或者 `checkport = true`、
`port_forward = "yes"` 同时开着，都等于对外宣告「我开了公网端口」。三项必须同时是关的。

**规则 6 是第二容易踩的**：应用中心按版本号判断是否需要安装，版本与已装箱相同会被当成同版本，
走不到完整安装链路。每次提交前必须升版本。

## 3. 提交前要做的事

版本号三处同步（漏一处就会带错版本出包）：

```bash
grep '^VER=' build.sh                    # 1
grep '^version ' manifest                # 2
head -3 CHANGELOG.md                     # 3
```

构建与校验：

```bash
bash build.sh
```

构建脚本会自己注入 `platform` 与 `checksum`，不要手工改包内的 `manifest`。

手动校验要点，两个包都要过：

```bash
VER=$(sed -n 's/^version *= *//p' manifest | tr -d ' ')
tar xzOf "dist/fnspeed_x86_${VER}.fpk" manifest | grep -E '^(version|platform|checkport|checksum)'
tar xzOf "dist/fnspeed_x86_${VER}.fpk" app.tgz | tar tzf - | grep -E 'ui/config|^\S*fnspeed$'
md5sum dist/*.fpk      # 与 manifest 的 checksum 逐位对比
```

**包必须与 GitHub Release 同源**。发布 tag 后 CI 会生成双架构包，优先直接下载 Release 资产
（本机走镜像 `https://gh-proxy.com/<原始URL>`），再 `sha256sum` 对一遍 Release 资产页的摘要。
不要用当前工作树的 `build.sh` 产物提交 —— 工作树可能含未发布提交，会出现「版本号相同、
行为不同」的包，审核与用户升级都会出问题。

`app.tgz` 里必须能看到 `./ui/config`。看不到就是「应用中心能装、图标点不开」，见
[docs/INSTALL.md](INSTALL.md#4-入口文件到底放在哪最容易踩的坑)。

### 「应用介绍」字段怎么填：首次上架 vs 更新上架

官方口径是：**初次上架描述应用是干嘛的，更新上架描述变更内容**。所以同一个字段在两次
提交里装的是不同的东西，别把功能介绍原样再交一遍（那等于没告诉审核这次改了什么），
也别在更新时只写「优化了若干问题」这种没信息量的话。

| 提交类型 | 表单「应用介绍」填 | 对应 manifest 字段 |
|---|---|---|
| 首次上架（新应用） | 功能介绍：这个应用解决什么问题、有哪些功能、怎么访问 | `desc` |
| 更新上架（已上架过的版本） | 变更内容：这次具体改了什么 | `changelog` |

两段文字的**唯一来源是 manifest 字段本身**（`desc` / `changelog`），把 `<br /><br />`
还原成空行、`<br />` 还原成换行、去掉 `<strong>` 标签即可。下面两段是从 1.6.1 的
manifest 里逐字还原的，改文案时改 manifest、再重新还原，别两边各写一份。

#### 更新上架用（= manifest 的 changelog，1.6.1）

```text
修正统计口径并补齐海外测速能力。

一、修正瞬时速率口径：改为 1 秒滑动窗口并统一服务端计算，波动大时不再出现远超物理链路的假数字（如 3 Gbps），曲线不再被单个尖峰压平。

二、爬坡提速：起始并发 4 条改为 8 条（海外源 12 条），小并发时翻倍加流，更快接近真实带宽拐点；主读数改为三帧中位数，不再沿用上一帧兜底。

三、延迟进入判定：按 RTT 折算每条流所需的在途数据（BDP），与内核允许的窗口比较，能区分「目标端限速」与「跨境 RTT 高、单流窗口受限」—— 后者加并发有效、加时长无效。链路面板新增「单流 BDP」。

四、海外源扩充：云端清单新增 Fastly、AWS CloudFront、Google、Hetzner 四家厂商与八源聚合分组；定向测速新增 17 个海外城市节点（逐个核对过归属地）。

五、新增可选「线路偏好 · 海外优先」（默认关闭）：开启后改用 Cloudflare / Google 公共 DNS 的加密查询解析测速源域名，让 CDN 交出海外节点；解析失败自动回落本机 DNS 并在端点行标注。关闭该开关时不会向这两家发起任何请求。

访问方式与隐私边界不变：仍只监听 127.0.0.1、经网关访问；出口与命中 IP 仍仅存内存。
```

若表单对该字段有长度限制（约 250 字），用这版精简的，五条要点与合规边界都还在：


#### 首次上架用（= manifest 的 desc，功能介绍）

```text
持续双向带宽压测：可增减的并发流把上行 / 下行压满，实时绘曲线，按「本机 / 链路 / 目标端」三层定位瓶颈。

用途边界：仅测自有或已获授权的链路；源为腾讯、阿里、苹果、微软等厂商公开分发地址，只读不写、不触碰业务系统。

主要功能
· 动态并发：8 流起跑（海外源 12 条），涨幅超 5% 加流，拐点自动锁定，千兆可跑满
· 双向压测：下行多流 GET（断流重连）；上行向自建接收端 POST
· 多源与云端：一集多址按负载分流；清单云端刷新，新增源不必重装，断网回落内置
· 定向测速：105 个测速位置（88 个「省 × 运营商」+ 17 个海外城市），EDNS + 强制拨号命中目标节点
· 自检与隐私：DNS / TCP / TLS / HTTP 逐层定位；出口与命中 IP 仅存内存

访问方式：桌面图标经 fnOS 网关打开，手机 App 与 FN Connect 可用；只监听 127.0.0.1，不开公网端口、不做端口转发。

开源：MIT，github.com/Jettype/fnspeed
```

写作口径：单项功能压到一行以内，用 `·` 不用 `1.`，避免换行后出现孤字。四项必须留——
用途边界（审查看是否攻击工具）、只读不写、只监听回环、开源地址；更新上架的文案里还要
带上「合规边界不变」的收尾句，审核最关心的是这一点有没有被改。

预览：`tools/preview_desc.js` 把 desc 渲染成详情页样式并出图（`tools/desc-preview.png`）。

审核追问补充两条：

| 追问 | 应答 |
|---|---|
| 「海外优先会不会绕过什么？」 | 它只影响测速源域名的 DNS 解析路径（换成 Cloudflare/Google 公共 DNS 的加密查询），让 CDN 按海外位置返回边缘节点；请求目标仍是清单里那些公开分发地址，且每条地址落地前照常过准入校验与授权勾选。默认关闭，不产生任何流量。 |
| 「1.6.1 的速率显示怎么修的？」 | 瞬时速率从「相邻两次采样的差值」改为 1 秒滑动窗口并统一在服务端计算：TCP 停滞后成批补发落在单个采样区间里，会把 150–200MB 除以 0.5 秒算出 3 Gbps，超过链路物理上限；窗口拉长后这类突发被摊平，峰值与曲线共用同一口径。 |

## 6. 审核可能的追问与应答

| 追问 | 应答 |
|---|---|
| 「这个能打别人网站，算不算攻击工具？」 | 默认源是厂商公开的软件分发包，单源并发受调度器限制，且启动前有授权确认。用户要测第三方站点必须自己填 URL，属于使用者责任，README 与关于页都有免责声明。 |
| 「为什么还需要联网？」 | 压测的性质决定必须联网取数据，否则测不出带宽。DNS 与 HTTP 全部走系统默认网络栈，没有自建代理或隧道。 |
| 「为什么不走网关，要开端口？」 | 已改。1.5.5 起只监听 127.0.0.1，对外只有网关一条路。 |
| 「跑起来占用多少资源？」 | 空闲时进程常驻约 15 MB 内存、CPU 近 0；满速压测时单核 5–15%，内存随并发线性增长（32 并发约 40 MB），不写磁盘。 |
| 「为什么启动要访问 GitHub？」 | 只是读一份测速源清单 JSON，用来在不重新打包的情况下补充和替换失效的测速地址。清单不含可执行内容，只被解析成 URL 列表；拉取失败、超时或内容不合格时一律回落到出厂清单，断网也能正常使用，设置里可以关闭。 |
| 「远端清单被篡改会不会变成攻击别人的跳板？」 | 清单里每条地址落地前都要过与用户手填地址相同的准入校验（只认 http/https、必须有主机名、长度上限），且压测前仍有授权勾选；配置了 HMAC 密钥时，签名不符的整份清单拒绝。 |
| 「云端清单多久更新一次，会不会刷 GitHub？」 | 默认 6 小时一次，清单自身可指定 5 分钟到 24 小时；失败后退避 1–30 分钟重试；内容未变时服务端返回 304，不重复下载。 |
